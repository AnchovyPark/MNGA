### 문서 정의(union)는 megacore launch skew 때문에 불통과

core별 event를 보니 core0의 `XLA Module` event가 core1보다 12~46µs 먼저 시작하고, core1이 끝날 때 같이 끝난다. core0이 core1의 launch를 기다리는 시간이며 실행마다 크게 흔들린다. 연산 자체(XLA Ops의 add fusion)는 8.3µs로 일정.

| 지표 | add1 fresh×5 min | 변동 | gate fresh×5 min | 변동 |
|---|---|---|---|---|
| union = 첫 시작~마지막 종료 (§4 정의) | 20.61~23.11 | 12% ✗ | 75.18~84.23 | 11% ✗ |
| **sync = 마지막 시작~마지막 종료** | 8.268~8.309 | **0.5%** ✓ | 68.405~68.421 | **0.02%** ✓ |

- **Module 1 대표값을 sync_min으로 쓴다.** 근거: (1) skew는 kernel과 무관한 launch 동기화. (2) 실제 model에서는 layer 하나가 executable 하나라 skew가 kernel마다가 아니라 executable마다 1번. (3) noise가 20배 이상 작다.
- data 행에는 §4 정의값(dev_min/med)도 그대로 남기고 sync 열을 뒤에 붙인다 → Module 2와 어느 쪽으로든 맞출 수 있다.
- **⚠ Module 2도 같은 skew를 겪는다. 두 VM이 같은 지표를 써야 U가 맞으니, Module 2에 sync 지표 공유 필요.**

- **gemm의 입력 사본 효과 +49%**: HLO에 `copy-start ... cross_program_prefetch_index=0`(weight를 `S(3)` 메모리 공간으로 prefetch)이 있다. 같은 weight buffer를 반복하면 이전 실행의 prefetch가 재사용돼 weight 로드가 숨는 것으로 보인다. 실제 model은 layer마다 weight가 달라 매 실행 다시 읽으므로 **사본 순환 쪽이 실제에 가깝다.** 지시대로 기본(같은 입력 반복)은 유지하고, gemm은 Step 3에서 사본 순환 값도 같이 기록한다.
- noise floor(이후 판정 기준): sync 기준 **0.5%**.

### model 정의
- P0 roofline (spec 275 TFLOPS, 1200 GB/s): 20~80% 오차. vector는 고정 비용(~1~4us)을 못 담아 크게 과소예측.
- P1 type별 `a + b·flops + c·bytes` (가중 최소제곱, 상대오차).
- P2 gemm = **CMEM을 구분하는 fitted roofline**: `a + max(C, Mm) + e·min(C, Mm)`, 전체 data fitted 계수가 spec과 맞는다: compute 271 TFLOPS(spec 275), activation 1135 GB/s, weight(HBM) 1166 GB/s(spec 1200), weight(CMEM) 2.9 TB/s, 고정 1.7us, overlap 누수 e=0.20.
- P2 vector = P1 + tile padding + `bytes·[M<1024]` (Step 2 계단), rope는 `+ e·M`. P1 대비 개선 거의 없음 → vector는 P1 채택.

### 발견 1: 같은 입력 반복 측정의 CMEM 효과 (gemm)
- M=128 gemm의 weight 실효 대역폭: weight ≤ 128 MiB(= v4 CMEM)이면 **~1.9 TB/s**(HBM peak 초과 → CMEM에서 읽음), 130 MiB 이상이면 **~0.97 TB/s**(HBM). 경계가 CMEM 용량과 일치.
- 같은 weight buffer를 반복하면 cross-program prefetch(`copy-start ... cross_program_prefetch_index=0`, `S(3)`)가 다음 실행용 weight를 CMEM에 올려 둔다. **실제 model(layer 수십 개 weight >> 128 MiB)에서는 일어나지 않는 측정 artifact.** P1의 큰 오차(43%)가 전부 weight > CMEM인 M=128 행이었다.
- → 실제에 가까운 값은 입력 사본 순환(copies8) 측정. 별도 data로 잰다(아래).
- **Module 2도 같은 입력 반복으로 window를 재므로 같은 artifact가 window에 섞인다. 공유 필요.**

### 발견 2: 128 정렬 안 된 K·N에서 lowering 계단
- 무작위 (K,N)은 64 배수라 128 정렬이 안 된 것이 있다. 예: (K,N)=(4032,7232)에서 M=768 244.0us, M=1024 246.6us (M 1.33배인데 시간 같음), M=256 83.3 vs M=128 43.3 vs M=384 98.9.
- gemm P2 T1 오차: **K,N 128 정렬 3.1%** (477행) vs 비정렬 6.4% (283행). T4도 2.9% vs 6.1%. Llama shape는 전부 128 정렬.
- Step 2 sweep은 256 간격이라 이 계단을 못 봤다.

### 발견 3: rope는 head 수에 따라 원소당 시간이 비단조
- M=4096 원소당 ns: HD=128에서 heads 2→0.030, 3→0.013, 4→0.017, 8→0.012. heads ≥ 8이면 0.009~0.012로 수렴.
- T2 오차 큰 행은 전부 heads ≤ 8 (`rope_k`: KV·HD = 256~1024). rows 항·head padding feature로 개선 안 됨 (10.6→10.3%).
- 목표 미달 조건: **rope, heads(N/HD) ≤ 8**. 실제 chain에서 `rope_k`가 여기 해당하나 kernel 자체가 작다(6~37us).

### T3 hi→lo (M ≥ 2048로 학습해 M ≤ 1024 예측)
- gemm P2 39%: 큰 M은 전부 compute-bound라 memory 항이 식별되지 않는다. P1은 11%. RNGD와 같은 결론(학습 범위 밖 외삽 약함). 작은 M 점이 학습에 필요하다.

## 2차 범위 (§3.3): attention core kernel, lm_head

### 정의 (`profiling/tpu_v4/kernels_attn.py`, 새 공통 파일. kernels.py는 안 건드림)

- layout은 CHAIN과 같다: q=rope_q [S,NH·HD], k=rope_k·v [S,KV·HD], 출력 attn_out [S,NH·HD]. GQA는 head h → kv h//(NH/KV). score [NH,S,S] bf16.
- `qk`, `scale`(·HD^-0.5), `mask`(causal, iota, bf16 최솟값), `softmax`(fp32 계산 → bf16), `av`, `attn`(다섯 개를 한 함수로 = TPU_INSTRUCTIONS Step 4의 attn token).
- TPU에서 fp32 참조(GQA repeat, 직접 계산)와 max|err| 0.014~0.018 (값 최대 ~3, bf16 수준). `attn_check.py`, `logs/attn_check.log`.
- **v4 + 이 JAX에서 online-softmax 치환은 없다.** fused attn은 score를 HBM에 materialize한다 (flash 아님). NH=40·S=512에서만 `ConcatBitcast` custom-call 하나.
- Module 2가 attention token을 붙일 때 이 파일을 쓰면 두 VM 정의가 같다.

### 측정

- 점: head 구성 19종 (크기 10종에서 9종 + model 밖 10종, seed 20261127) × S 10종. qk·av·attn은 (S,NH,KV,HD), scale·mask·softmax는 (S,NH)로 중복 제거 → 900점. `gen_points_attn.py`, `points_attn*.txt`. 행 형식은 KROW 그대로, M=S, K=NH, N=KV.
- same 900점: scale 110점 실패 (내 버그: elementwise 점의 HD=0으로 `0**-0.5`). 실패 행은 `attn/data_attn_tpu_v4.txt`에 남기고 `data_attn_scale_tpu_v4.txt`에 재측정 (HD=0이면 scale 상수에 128을 쓴다. 1.0이면 XLA가 곱셈을 지운다).
- 사본 2개 순환 900점 (`data_attn_copies2_tpu_v4.txt`), 실패 0.

**copies2 / same**: av만 다르다. score 입력 ≤ 128 MiB에서 same이 1.2~3.6배(평균 2.06) 빠르다 (score 입력을 CMEM에서 재사용). > 128 MiB 1.000. 나머지 type은 전부 1.000 ± 0.5% → **attention은 copies2를 기준 data로 쓴다.**

| kernel | 시간 | 내용 |
|---|---|---|
| qk HD64 / HD128 | 814 / 850 us | convolution(score를 이상한 layout으로 씀) 254 us + **score를 기본 layout으로 바꾸는 copy 546 us (67%)** |
| av | 279 / 291 us | score 읽는 convolution 266 us |
| softmax | 824 us | reduce(max) 264 + exp·sum·normalize fusion 561 |
| attn (fused) | 834 / 880 us | score pass 3번 (qk+scale+mask+rowmax → sum exp → av+normalize), 각 ~260 us |

- 시간은 **score 원소 수(NH·S²) × HBM pass 수**로 정해진다. HD 64↔128은 거의 차이 없음 (flops 2배인데 시간 +4%).
- score pass 1번 ≈ 1 TB/s.
- **attn(fused) / 다섯 kernel 단독 합 = 0.23~0.35** (S별 평균, copies2). 단독 kernel 합으로 attention을 만들면 3~4배 과대. qk 단독의 relayout copy와 중간 score의 반복 읽기·쓰기가 fused에서는 사라진다.

### 128 MiB 경계 (copies2에서도 있음 → 재사용 artifact가 아니라 XLA의 program 안 CMEM 배치)

score 원소당 시간 (ps), S ≥ 512:

| type | score < 128 MiB | ≥ 128 MiB |
|---|---|---|
| qk | 3.2~6.0 (크기 클수록 작아짐) | 6.0~6.3 |
| av | 2.7~4.9 | 2.0~2.3 |
| softmax | 8~16 (S가 작을수록 큼: 행당 비용) | 6.0 |
| attn | 4.9~10.5 | 5.9~6.9 |
| scale, mask | 4.0~4.5 | 4.0~4.3 (변화 없음) |

경계에 딱 맞는 128 MiB 점은 섞여 있다 (qk 2048·16·64는 '들어감'처럼, 1024·64·128은 '안 들어감'처럼).

### fitting (`fit_attn.py`, copies2, `attn/fit_attn_copies2.log`)

model: P0 roofline, P1 a+b·flops+c·bytes, P2 a+b·NH·S²+c·(NH+KV)·S·HD+d·NH·S (elementwise는 a+b·NH·S²+c·NH·S), **P3 = P2에서 NH·S² 항을 score < 128 MiB 여부로 둘로 나눈 것**.

| type | P1 T1 / T2 | P2 T1 / T2 | **P3 T1 / T2** | P3 T4 (model→rand) |
|---|---|---|---|---|
| qk | 19.6 / 19.5 | 19.5 / 19.1 | **6.9 ✗ / 7.8** | 7.2 |
| scale | 3.8 / 4.3 | 3.0 / 3.8 | **3.0 / 3.8** | 4.6 |
| mask | 4.6 / 3.9 | 4.1 / 3.8 | **4.2 / 3.7** | 4.0 |
| softmax | 24.4 / 28.2 | 5.2 / 5.0 | **3.6 / 3.8** | 4.4 |
| av | 13.4 / 14.0 | 8.7 / 8.4 | **3.6 / 3.2** | 3.7 |
| attn | 18.0 / 16.3 | 7.2 / 6.7 | **4.4 / 3.9** | 4.1 |

- **P3 채택.** T2(≤10%)는 전부, T1(≤5%)은 qk 빼고 충족.
- qk가 깨지는 조건: (1) score가 128 MiB 경계에 딱 걸린 점 (2048·16·4·64 오차 78%), (2) head 적은 HD=128 구성(16·4·128)의 작은 S (15~30%).
- T3(S 외삽)는 lo→hi qk 28%, av 37%, attn 11%: 외삽 방향으로 128 MiB 경계를 넘기 때문. hi→lo는 수백 %. **S는 학습 범위 안에서만 쓴다.**
- same data로 해도 P3는 비슷 (av만 T1 10.3%: CMEM 재사용 artifact). `attn/fit_attn_same.log`.

### lm_head (gemm M=1, K=D, N=128256) — gemv 경로와 N cliff

- **M=1 gemm은 XLA가 matmul(convolution)이 아니라 `multiply_reduce_fusion`(kLoop, vector unit)으로 바꾼다.** M=8부터는 convolution.
- lm_head 측정 (`attn/data_lmhead_tpu_v4.txt`, M ∈ {1,8,128,512} × D 8종): M=1이 M=8보다 **2.1배 느리다** (weight 479 GB/s vs ~1010 GB/s). copies2 = same (weight > CMEM).
- M=1을 step3의 (K,N) 76쌍에서 재면 (`data_gemv_tpu_v4.txt`) 820~1000 GB/s, model `a + c₁·2KN + c₂·2K + c₃·2N` T1 MAPE 1.9%. N 32768~152064로 외삽해도 +3~4%.
- **그런데 특정 N에서 대역폭이 떨어진다** (K=2048, N=128·t, `data_gemv_nsweep/cliff`): t 504~516 → 745 GB/s, t 1001~1004 → 479, **t 1008 → 1008 (정상)**, t 1016~1024 → 479, t 1025 → 641, 그 밖 (480·496·520·960·1000·1032·1056·1088·1188) → ~1000. K=4096도 같다. HLO 연산 목록은 모두 같다. 규칙을 찾지 못함 (codegen의 tiling 선택으로 추정).
- **Llama-3 vocab 128256 = t 1002가 바로 이 구간이다.** 예측하면 −50%. → lm_head는 측정값을 쓴다 (TPU_INSTRUCTIONS Step 6도 lm_head는 단독 측정값).
- Step 4의 gemm P2를 lm_head M ≥ 8로 외삽: same은 M=8 −12%, M=128 −3.7%, M=512 +10%. **copies8 계수는 M=8 −62%, M=128 −22%**: copies8 data에서 큰 weight(>128 MiB) 행이 모두 M ≥ 128 (compute 지배)이라 큰 weight 대역폭이 2.9 TB/s(불가능한 값)로 잡혔다. HBM peak 하한을 두면 M=8 −15%까지 오지만 학습 범위 안 T1이 4.0→5.5%(목표 밖)가 되어 채택하지 않았다 (`fit_step4.py` 주석). → **copies8 gemm 계수는 학습 범위(M ≥ 128, weight ≤ 141 MB) 밖에서 쓰지 않는다.**
- 128 MiB 구분을 뺀 P2n(`--p2n`)은 copies8에서도 P2보다 나쁘다 (T1 7.2 vs 4.0%): 사본 순환에서도 작은 weight가 byte당 느린 것은 실제 현상.

### predict.py 추가
