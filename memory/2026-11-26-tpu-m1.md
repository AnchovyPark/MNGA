## Step 1. 측정 경로 확인 (gate) — 통과 (단 지표 변경, 아래)

1B, seq 512. log `profiling/tpu_v4/module1/logs/step1_run2.log`.

### 문서 정의(union)는 megacore launch skew 때문에 불통과

core별 event를 보니 core0의 `XLA Module` event가 core1보다 12~46µs 먼저 시작하고, core1이 끝날 때 같이 끝난다. core0이 core1의 launch를 기다리는 시간이며 실행마다 크게 흔들린다. 연산 자체(XLA Ops의 add fusion)는 8.3µs로 일정.

| 지표 | add1 fresh×5 min | 변동 | gate fresh×5 min | 변동 |
|---|---|---|---|---|
| union = 첫 시작~마지막 종료 (§4 정의) | 20.61~23.11 | 12% ✗ | 75.18~84.23 | 11% ✗ |
| **sync = 마지막 시작~마지막 종료** | 8.268~8.309 | **0.5%** ✓ | 68.405~68.421 | **0.02%** ✓ |

- **Module 1 대표값을 sync_min으로 쓴다.** 근거: (1) skew는 kernel과 무관한 launch 동기화. (2) 실제 model에서는 layer 하나가 executable 하나라 skew가 kernel마다가 아니라 executable마다 1번. (3) noise가 20배 이상 작다.
- data 행에는 §4 정의값(dev_min/med)도 그대로 남기고 sync 열을 뒤에 붙인다 → Module 2와 어느 쪽으로든 맞출 수 있다.
- **⚠ Module 2도 같은 skew를 겪는다. 두 VM이 같은 지표를 써야 U가 맞으니, Module 2에 sync 지표 공유 필요.**

### 그 외

| 항목 | 결과 |
|---|---|
| event 수 | 모든 측정에서 30/30 |
| fresh vs 한 process 연속(14 window) | sync 기준 동일 (add1 8.27~8.30, gate 68.39~68.42) → **fresh process 불필요** |
| dispatch overhead (wall_min − sync_min) | add1 ≈ 137µs, gate ≈ 140µs (호출당 ~135~145µs) |
| `kn.window(i,i+1)` vs `kn.KERNELS[type]` 단독 | 같음 (add1 8.26 vs 8.28, gate 68.41 vs 68.39) |
| 같은 입력 반복 vs 입력 사본 8개 순환 | add1 8.28 vs 8.29 (차이 없음). **gate 68.39 vs 101.68 (+49%)** |

- **gemm의 입력 사본 효과 +49%**: HLO에 `copy-start ... cross_program_prefetch_index=0`(weight를 `S(3)` 메모리 공간으로 prefetch)이 있다. 같은 weight buffer를 반복하면 이전 실행의 prefetch가 재사용돼 weight 로드가 숨는 것으로 보인다. 실제 model은 layer마다 weight가 달라 매 실행 다시 읽으므로 **사본 순환 쪽이 실제에 가깝다.** 지시대로 기본(같은 입력 반복)은 유지하고, gemm은 Step 3에서 사본 순환 값도 같이 기록한다.
- noise floor(이후 판정 기준): sync 기준 **0.5%**.

### chip 병렬

4개 chip을 process별로 하나씩(`TPU_VISIBLE_CHIPS=c`) 써서 측정 점을 나눠 잰다 (`run_parallel.sh`). 같은 4점을 chip 0~3에서 잰 sync_min: add 8.256~8.307, gemm(512,2048,8192) 68.426~68.446, gemm(2048,4096,14336) 896.528~896.567, silu 34.69~34.83 → **chip 사이 차이 ≤0.6% (noise floor 수준)**. 지시서의 "device 1개"는 process당 1개로 지킨다.

- **유일한 계단: add, M 960→1024에서 14.87→13.72us (−7.7%)**. 단위당 시간이 M<1024에서 0.0155, M≥1024에서 0.0134us로 한 단계 낮아진다. HLO 연산 목록은 바뀌지 않는다(같은 `add` 한 개) → op 종류가 아니라 tiling 등 내부 lowering 선택이 바뀐 것으로 추정. vector kernel 예측에서 M=1024 경계를 feature 후보로 둔다.
- gemm N·K 축의 1~2% 톱니는 규칙이 없고 noise floor(0.5%)의 2~3배 수준이다.
- 결론: Step 3의 M 목록(128..4096, 10점)과 log-uniform (K,N) sampling을 그대로 쓴다. 촘촘히 더 잴 구간은 없다 (add의 M=1024 경계는 M 목록에 이미 768/1024가 있다).

### model 정의
- P0 roofline (spec 275 TFLOPS, 1200 GB/s): 20~80% 오차. vector는 고정 비용(~1~4us)을 못 담아 크게 과소예측.
- P1 type별 `a + b·flops + c·bytes` (가중 최소제곱, 상대오차).
- P2 gemm = **CMEM을 구분하는 fitted roofline**: `a + max(C, Mm) + e·min(C, Mm)`, 전체 data fitted 계수가 spec과 맞는다: compute 271 TFLOPS(spec 275), activation 1135 GB/s, weight(HBM) 1166 GB/s(spec 1200), weight(CMEM) 2.9 TB/s, 고정 1.7us, overlap 누수 e=0.20.
- P2 vector = P1 + tile padding + `bytes·[M<1024]` (Step 2 계단), rope는 `+ e·M`. P1 대비 개선 거의 없음 → vector는 P1 채택.

### 발견 1: 같은 입력 반복 측정의 CMEM 효과 (gemm)
- M=128 gemm의 weight 실효 대역폭: weight ≤ 128 MiB(= v4 CMEM)이면 **~1.9 TB/s**(HBM peak 초과 → CMEM에서 읽음), 130 MiB 이상이면 **~0.97 TB/s**(HBM). 경계가 CMEM 용량과 일치.
- 같은 weight buffer를 반복하면 cross-program prefetch(`copy-start ... cross_program_prefetch_index=0`, `S(3)`)가 다음 실행용 weight를 CMEM에 올려 둔다. **실제 model(layer 수십 개 weight >> 128 MiB)에서는 일어나지 않는 측정 artifact.** P1의 큰 오차(43%)가 전부 weight > CMEM인 M=128 행이었다.
- → 실제에 가까운 값은 입력 사본 순환(copies8) 측정. 별도 data로 잰다(아래).
- **Module 2도 같은 입력 반복으로 window를 재므로 같은 artifact가 window에 섞인다. 공유 필요.**

### 발견 2: 128 정렬 안 된 K·N에서 lowering 계단
- 무작위 (K,N)은 64 배수라 128 정렬이 안 된 것이 있다. 예: (K,N)=(4032,7232)에서 M=768 244.0us, M=1024 246.6us (M 1.33배인데 시간 같음), M=256 83.3 vs M=128 43.3 vs M=384 98.9.
- gemm P2 T1 오차: **K,N 128 정렬 3.1%** (477행) vs 비정렬 6.4% (283행). T4도 2.9% vs 6.1%. Llama shape는 전부 128 정렬.
- Step 2 sweep은 256 간격이라 이 계단을 못 봤다.

### 발견 3: rope는 head 수에 따라 원소당 시간이 비단조
- M=4096 원소당 ns: HD=128에서 heads 2→0.030, 3→0.013, 4→0.017, 8→0.012. heads ≥ 8이면 0.009~0.012로 수렴.
- T2 오차 큰 행은 전부 heads ≤ 8 (`rope_k`: KV·HD = 256~1024). rows 항·head padding feature로 개선 안 됨 (10.6→10.3%).
- 목표 미달 조건: **rope, heads(N/HD) ≤ 8**. 실제 chain에서 `rope_k`가 여기 해당하나 kernel 자체가 작다(6~37us).

### T3 hi→lo (M ≥ 2048로 학습해 M ≤ 1024 예측)
- gemm P2 39%: 큰 M은 전부 compute-bound라 memory 항이 식별되지 않는다. P1은 11%. RNGD와 같은 결론(학습 범위 밖 외삽 약함). 작은 M 점이 학습에 필요하다.
