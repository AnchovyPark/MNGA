### 발견: core launch skew

trace에서 실행 1회마다 `/device:TPU:0`, `/device:TPU:1` 두 plane이 `XLA Modules` event를 하나씩 남긴다.
core 0이 core 1보다 **13~30µs 먼저 시작해 기다리는** 일이 무작위로 생긴다. 실제 연산(`XLA Ops`)은 두 core가 같은 시점에 시작해 같은 시점에 끝난다.
공통 문서 §4의 union 정의(첫 시작~마지막 종료)는 이 skew를 그대로 포함한다.

- `sync` = 마지막 종료 − 가장 늦은 시작. skew를 뺀 실행 시간.
- data 행 끝에 `sync_min_us sync_med_us` 두 열을 추가했다. 앞의 `dev_min_us dev_med_us`는 문서 정의(union) 그대로다.
- **이후 분석은 `sync_min_us`를 쓴다.**

### 결과 (fresh process 5회, min 값의 범위)

| token | union min (µs) | 변동 | sync min (µs) | 변동 | wall min (µs) |
|---|---|---|---|---|---|
| `add1` | 18.1 ~ 23.1 | 27% | 8.267 ~ 8.280 | **0.16%** | 141 ~ 165 |
| `gate` | 77.6 ~ 83.5 | 7.6% | 68.395 ~ 68.417 | **0.03%** | 195 ~ 206 |

- union 기준이면 `add1`이 통과 조건(5%)을 못 넘는다. sync 기준이면 둘 다 0.2% 이하다.
- **fresh process 불필요**: 43 window를 한 process에서 연달아 잰 뒤의 `add1` 8.29, `gate` 68.37~68.42 = fresh와 0.3% 안에서 같다 (RNGD와 다름).
- dispatch overhead (wall − sync) ≈ 130µs/호출. host timing으로는 kernel을 잴 수 없다는 공통 문서 판단과 일치.
- **noise floor ≈ 0.3%** (sync 기준).

- 같은 weight buffer를 반복하면 gemm의 weight HBM load(32MB ≈ 33µs)가 사라진다. compile된 module 앞부분에 weight를 `S(3)` memory space로 옮기는 `copy-start/done`이 있는데, 같은 buffer면 0.04µs로 끝난다.

### 진단 1: chain이 서로 연결되지 않은 두 덩어리다

`attn_out`이 외부 입력이라 Tokenwise chain = A(`norm1..v`, token 0~5) + B(`o..add2`, token 6~14), 둘 사이 data 의존 없음.
full(0:15)의 trace를 보면 XLA가 **B(MLP)를 먼저, A(q/k/v)를 나중에** 실행하고, 끝에 weight prefetch 대기(`slice-done` 27.6µs, seq 512)가 남는다.
즉 full은 chain 순서대로 돌지 않으므로 chain 순서의 telescope와 구조가 다르다. 실제 model에서는 사이에 attention이 있어 이 재배치가 일어나지 않는다.

덩어리별로 따로 telescope (`analyze_subchain.py`, 덩어리 window 0:6, 6:15를 추가 측정):

| 방식 | seq | A tele3 | A tele5 | B tele3 | B tele5 | (A+B)/full(0:15) |
|---|---|---|---|---|---|---|
| 같은 입력 | 512 | 1.048 | 1.018 | 0.949 | 1.007 | 0.917 |
| 같은 입력 | 2048 | 0.967 | 0.963 | 0.842 | 0.925 | 0.984 |
| 사본 2개 | 512 | 1.037 | 1.015 | 1.051 | 1.022 | 0.944 |
| 사본 2개 | 2048 | 0.968 | 0.964 | 0.861 | 0.919 | 0.990 |

- A(q/k/v)는 3-gram으로 3~5% 안에 든다.
- B(o·MLP)는 seq 512에서는 5% 안, **seq 2048에서 14~16% 과소**. 5-gram에서도 7~8%.
- seq 512에서는 두 덩어리를 한 함수로 묶은 것 자체가 따로 잰 합보다 6~8% 느리다 (XLA 재배치·prefetch 대기 비용).

### 진단 2: window 경계가 XLA fusion을 바꾼다 (MLP diamond)

- full의 HLO: `norm2`는 `gate`·`up` gemm fusion 각각의 prologue로 들어가고(두 번 계산), `silu·mul`은 `down` gemm fusion의 prologue로 들어간다.
- window는 밖에서 쓰이는 값만 반환하므로, 경계가 어디냐에 따라 materialize되는 tensor가 달라진다.
  예 (같은 입력, seq 2048): `W2(silu+up)` = 337.5 > `W3(silu+up+mul)` = 289.4. `mul`을 window에 넣으면 `silu` 출력([S,INTER])을 쓰지 않아도 돼서 48µs **줄어든다**. marginal이 음수가 된다.
- `norm2 → gate, up → mul`은 token 8~12에 걸친 diamond라 3-gram window 안에 다 들어오지 않는다.

### Step 2 결론 (잠정)

1. 15-token chain 전체 그대로의 kernel 단위 n-gram(≤5)은 TPU v4에서 성립하지 않는다.
2. 주된 원인은 (a) 독립 두 덩어리의 XLA 재배치, (b) seq가 클 때 MLP diamond 주변의 fusion 경계 효과다.
3. q/k/v 덩어리는 3-gram으로 성립(≤5%)하고, MLP 덩어리는 seq 512에서만 성립한다.

- 목표(E1 W3 ≤ 5%, M0보다 noise floor 이상 개선) **달성**: 19.5% → 2.9% (copies2), 16.6% → 4.0% (copies1).
- seq 2종(512, 2048)만 쓴 최소 결과도 E1 2.6% (copies2) / 3.0% (copies1). 그때는 E2(seq 외삽)가 5~16%로 나빴고, seq 4종이 되면서 4~5%로 내려왔다. ridge는 seq 외삽에 약하다 (seq 2종일 때 E2 14~22%).
- 오차가 큰 window: `mul+down+add2`, `silu+up+mul`, `up+mul+down` (MLP diamond 주변), 작은 크기(1024·1536)의 seq 2048.

**결론 두 문장**
- output은 **r3 = W3 / ΣU** 로 한다 (log W 직접 학습보다 모든 split에서 낫다: 2.86 vs 5.12).
- input은 **S1 (type 순서 + U + token별 flops·weight bytes)** 까지 필요하다. S0만으로는 copies2에서 3.9%로 목표 안이지만 copies1에서 5.3%. S2·S3는 S1 대비 noise 수준의 개선이라, shape를 직접 넣을 필요는 없다 (= Module 2가 U를 거치는 구조가 의미 있다).
