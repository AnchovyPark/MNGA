### 발견: core launch skew

trace에서 실행 1회마다 `/device:TPU:0`, `/device:TPU:1` 두 plane이 `XLA Modules` event를 하나씩 남긴다.
core 0이 core 1보다 **13~30µs 먼저 시작해 기다리는** 일이 무작위로 생긴다. 실제 연산(`XLA Ops`)은 두 core가 같은 시점에 시작해 같은 시점에 끝난다.
공통 문서 §4의 union 정의(첫 시작~마지막 종료)는 이 skew를 그대로 포함한다.

- `sync` = 마지막 종료 − 가장 늦은 시작. skew를 뺀 실행 시간.
- data 행 끝에 `sync_min_us sync_med_us` 두 열을 추가했다. 앞의 `dev_min_us dev_med_us`는 문서 정의(union) 그대로다.
- **이후 분석은 `sync_min_us`를 쓴다.**

### 결과 (fresh process 5회, min 값의 범위)

| token | union min (µs) | 변동 | sync min (µs) | 변동 | wall min (µs) |
|---|---|---|---|---|---|
| `add1` | 18.1 ~ 23.1 | 27% | 8.267 ~ 8.280 | **0.16%** | 141 ~ 165 |
| `gate` | 77.6 ~ 83.5 | 7.6% | 68.395 ~ 68.417 | **0.03%** | 195 ~ 206 |

- union 기준이면 `add1`이 통과 조건(5%)을 못 넘는다. sync 기준이면 둘 다 0.2% 이하다.
- **fresh process 불필요**: 43 window를 한 process에서 연달아 잰 뒤의 `add1` 8.29, `gate` 68.37~68.42 = fresh와 0.3% 안에서 같다 (RNGD와 다름).
- dispatch overhead (wall − sync) ≈ 130µs/호출. host timing으로는 kernel을 잴 수 없다는 공통 문서 판단과 일치.
- **noise floor ≈ 0.3%** (sync 기준).

### 입력 사본 (§5 항목 5) — 5% 이상 차이, 기록

| window | 같은 입력 반복 (기본) | 사본 2개 | 사본 4개 |
|---|---|---|---|
| `add1` | 8.27 | — | 8.28 |
| `gate` | 68.41 | 101.83 | 101.69 |
| `down` | 68.16 | 101.45 | 101.37 |
| `gate+silu+up` | 140.10 | 173.66 | 173.62 |
| full (15 token) | 317.33 | 335.05 | 334.97 |

(sync min, µs. 사본 2개와 4개가 같으므로 원인은 캐시 용량이 아니라 "직전 호출과 같은 buffer인가"다.)

- 같은 weight buffer를 반복하면 gemm의 weight HBM load(32MB ≈ 33µs)가 사라진다. compile된 module 앞부분에 weight를 `S(3)` memory space로 옮기는 `copy-start/done`이 있는데, 같은 buffer면 0.04µs로 끝난다.
- 단독 gemm은 +49%, full window는 +5.6%만 늘어난다. 즉 **window 안에서는 weight load가 앞 kernel 계산 뒤에 숨는데, 같은 입력 반복은 단독 `U`에서 그 load를 지워 버린다.** `r2`, `r3`, `uni/full`이 측정 방식에 따라 크게 달라진다.
- 실제 model은 layer마다 weight가 다르므로 사본 방식이 실제에 가깝다.
- 공통 문서대로 기본 방식(같은 입력 반복)은 바꾸지 않는다. Step 2에서는 두 방식(copies=1, copies=2)을 모두 측정해 판정을 따로 낸다. Module 1과 맞출 방식은 사용자 결정 사항이다.
